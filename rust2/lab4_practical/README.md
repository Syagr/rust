# Практична робота 4 — Інтеграція багтрекінгової системи

В цій папці зібрані матеріали для Практичної роботи 4: приклади баг-репортів, рішення і опис інтеграції з GitHub Issues.

Файли:
- `FINAL_REPORT.md` — короткий звіт і інструкції для викладача.
- `SOLUTION.md` — рішення, опис багів і команди для виправлень.
- `issues/` — приклади баг-репортів (markdown).

Як використовувати: скопіюйте вміст `issues/*.md` у GitHub Issues або створіть issue через веб/CLI, потім створіть гілки з виправленнями і PR.
# Практична робота 4 — Порівняння багтрекінгових систем

Тема: Порівняння різних багтрекінгових систем.

Мета: Ознайомитися із функціоналом багтрекінгових систем, їх призначенням, та функціоналом.

Структура папки:
- `README.md` — цей файл (огляд та відповіді на контрольні питання).
- `integration.md` — інструкція інтеграції (GitHub Issues) та приклади команд.
- `issues/` — приклади баг-репортів (Markdown) які створені для проекту.
- `fixes/` — опис змін у коді та посилання на файли, що виправлено.

---

**Відповіді на контрольні питання**

1) Що таке багтрекінгова система?

  Багтрекінгова система — це інструмент для фіксації, відстеження та управління дефектами (багами), задачами та запитами у програмному забезпеченні. Вона дозволяє створювати репорти про проблеми, призначати їх, відстежувати статус виконання та зберігати історію змін.

2) Для чого використовуються багтрекінгові системи?

  - Фіксація багів, задач і запитів на зміни.
  - Призначення власників і встановлення пріоритетів.
  - Планування релізів та відстеження прогресу.
  - Збір метрик якості та часу на виправлення.

3) Які можуть бути вимоги до багтрекінгових систем?

  - Зручний інтерфейс для створення і редагування тасків.
  - Підтримка ролей і прав доступу.
  - Інтеграція з VCS (git), CI/CD та каналами комунікації (Slack, email).
  - Можливість створення кастомних полів, фільтрів та звітів.
  - API для автоматизації та інтеграції.
