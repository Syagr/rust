Лабораторна робота 8 — Налаштування асинхронного рантайму для кращої продуктивності

Тема: Налаштування асинхронного рантайму у проєкті з попередньої лабораторної роботи (`rust2/lab5`).

Коротко виконаного:
- Додано CLI-параметри для налаштування рантайму у `rust2/lab5`: `--rt-workers`, `--max-blocking`, `--thread-name`.
- Замість `#[tokio::main]` рантайм будується вручну через `tokio::runtime::Builder`, щоб можна було експериментувати з параметрами.
- Надано приклади запусків для порівняння часу виконання під різними параметрами.

Експерименти (як повторити локально)

1) Побудуйте релізну збірку:
```powershell
cd C:\It\projects\rust\rust2\lab5
cargo build --release
```

2) Згенеруйте тестові зображення (наприклад, 50 штук):
```powershell
cargo run --manifest-path C:\It\projects\rust\rust2\lab5\Cargo.toml --release -- gen-images --out sample_images --count 50
```

3) Запустіть обробку з різними параметрами рантайму і порівняйте вивід (зверніть увагу на рядки "Starting tokio runtime" і на друковані тривалості):
```powershell
# Конфіг 1: мало воркерів
cargo run --manifest-path C:\It\projects\rust\rust2\lab5\Cargo.toml --release -- --rt-workers 2 --max-blocking 64 process-images --dir sample_images --out sample_out --width 100 --workers 4

# Конфіг 2: більше воркерів
cargo run --manifest-path C:\It\projects\rust\rust2\lab5\Cargo.toml --release -- --rt-workers 8 --max-blocking 256 process-images --dir sample_images --out sample_out --width 100 --workers 4
```

Що фіксувати в результатах
- Час однониткової обробки (виводиться як "Single-threaded duration").
- Час паралельної обробки з вказаною кількістю робітників (виводиться як "Threaded duration(...)").
- Вплив `--rt-workers` (кількість воркерів рантайму) і `--max_blocking` (максимум блокуючих потоків) на швидкодію для вашого робочого навантаження.

Короткі висновки / поради
- Параметри, що найбільше впливають: `worker_threads` (кількість робочих потоків рантайму) і `max_blocking_threads`. Вони визначають паралелізм для асинхронних задач і для блокуючих операцій відповідно.
- Не завжди більше — краще: занадто багато воркерів створює конкуренцію за CPU, більше контекстних перемикань і погіршення кешування; оптимальне значення часто близьке до числа апаратних ядер або трохи більше, залежно від характеру роботи (I/O-bound vs CPU-bound).
- Blocking thread pool дозволяє виконувати блокуючі/CPU-bound операції (через `spawn_blocking`) не блокуючи асинхронні воркери; його розмір має бути достатнім для охоплення пікових блокуючих задач, але надто великий пул також створює накладні витрати.

Відповіді на контрольні питання
1) Які параметри рантайму впливають найбільше?
- `worker_threads` — кількість потоків, які виконують неблокуючі задачі. Визначає верхню межу одночасного виконання асинхронного коду.
- `max_blocking_threads` — розмір пулу для `spawn_blocking`, впливає на паралельність блокуючих операцій.
- Інші: налаштування планувальника, прапори `enable_io`/`enable_time` (вмикають I/O / таймери), іменування потоків для діагностики.

2) Чому велика кількість потоків не завжди краща?
- Дисципліна в плануванні: при CPU-bound навантаженні додаткові потоки призводять до перемикань контексту і конкуренції за кеш/CPU. Якщо завдання CPU-bound, оптимум приблизно співпадає з числом фізичних/логічних ядер.
- Для I/O-bound задач помірне збільшення воркерів корисне, але після певного порогу виграш зменшується.

3) Навіщо в tokio blocking thread pool?
- Щоб виконувати блокуючі або дорогі CPU операції без блокування асинхронних воркерів. `spawn_blocking` делегує роботу у цей пул і повертає майбутнє, яке пробудиться після завершення.
