Практична робота 9 — Використання екосистеми для покращення асинхронного коду

Тема: Покращити реалізацію з Практичної роботи 7, застосувавши можливості `futures` та `tokio`.

Що зроблено
- Замінив блокуючу файлову ітерацію на асинхронну (`tokio::fs::read_dir`) — реалізовано `collect_files_async`.
- Побудовано пайплайн для шифрування: `stream::iter(files) -> async read -> spawn_blocking(encrypt) -> async write` з`buffer_unordered` для контролю паралелізму.
- Для обробки зображень реалізовано паралельний варіант через `stream::iter(files).buffer_unordered(workers)`; важка обробка (resize) виконується в `spawn_blocking`.
- Видалено застарілий `walkdir`-блокуючий підхід та імпорти, які більше не використовуються.

Чому ці зміни покращують код
- `futures::stream::buffer_unordered` дає простий і ефективний спосіб контролювати паралелізм асинхронних операцій без ручного створення тасків/семафорів.
- Читання і запис файлів виконуються асинхронно (`tokio::fs`), тому операції I/O не блокують воркер-потоки рантайму.
- `spawn_blocking` використовується для CPU-bound роботи, щоб не блокувати асинхронні воркери.

Контрольні питання
1) Для чого використовується крейт `futures`?
- Надає низькорівневі і високорівневі абстракції для роботи з `Future` та потоками (`Stream`), корисні функції для комбінування, буферизації та обробки наборів майбутніх значень (наприклад, `buffer_unordered`, `join_all`).

2) Які інструменти у `tokio` полегшують роботу з асинхронним кодом?
- Рантайм (`Runtime`/`#[tokio::main]`), асинхронні I/O (файлова система, TCP/UDP), таймери, канали, `spawn_blocking` та синхронізаційні примітиви (`Semaphore`, `Mutex` у tokio), і утиліти для відлагодження/трасування.

3) Чому погано використовувати синхронний `Mutex` між `await` викликами?
- Синхронний `Mutex` може блокувати потік рантайму під час `await`, що призводить до зниження пропускної здатності; замість нього використовуйте `tokio::sync::Mutex` або реструктуруйте код, щоб уникати утримування блокувань через `await`.

4) Чому аргументи асинхронної задачі, яку ми `spawn`-имо, мають бути `'static`?
- `tokio::spawn` виконує задачу на незв'язаному життєвістю воркері; щоб гарантувати безпечність доступу до даних після виходу функції, всі дані, переміщені у задачу, мають жити на стек/купі довше за задачу — тобто бути `'static` або володіти власністю.

## Лабораторна робота 9 — Рефакторинг і покращення асинхронного коду

**Тема:** Рефакторинг програми з попередньої роботи — застосування можливостей `futures` і `tokio` для оптимізації асинхронного виконання.

**Короткий огляд змін**
- Файлова ітерація замінена на асинхронну: реалізовано `collect_files_async` через `tokio::fs::read_dir`.
- Побудовано стрім-пайплайни для обробки файлів: `futures::stream::iter(files)` → `map(async { read })` → CPU-bound в `spawn_blocking` → `fs::write` із `buffer_unordered` для контролю паралелізму.
- Для обробки зображень додано одночасний запуск через `stream::iter(...).buffer_unordered(workers)`, при цьому операції декоду/ресайзу виконуються в `spawn_blocking`.
- Додано підкоманду `gen-images` для генерування валідних тестових PNG-файлів.
- Ручна побудова рантайму (`tokio::runtime::Builder`) дозволяє тонко налаштувати `worker_threads` і `max_blocking_threads` для вимірів.

**Чому це покращує програму**
- Асинхронні I/O (`tokio::fs`) звільняють воркери рантайму від блокування під час читання/запису.
- `buffer_unordered` забезпечує простий контроль за кількістю одночасних завдань, без ручних семафорів або явного спавну великої кількості тасків.
- `spawn_blocking` відокремлює CPU-bound роботу (декодування/ресайз, шифрування) від async-воркерів, запобігаючи деградації продуктивності.

**Використані crate/функції**
- `tokio` — асинхронний рантайм, `fs`, `spawn_blocking`, runtime builder.
- `futures` — `stream::iter`, `StreamExt`, `buffer_unordered`, `for_each`.
- `image` — читання/декодування/ресайз зображень у `spawn_blocking`.
- `aes-gcm` — шифрування у `spawn_blocking`.

## Відповіді на контрольні питання (9.2)

1) Як компілятор визначає розмір `Future`?

 - Коли ви пишете `async fn`, компілятор створює анонімний тип (машину станів) — структуру, що містить усі локальні змінні й захоплення, які живуть через `await` точки. Розмір `Future` дорівнює розміру цієї структури, і він відомий час компіляції. Якщо `Future` захоплює великі буфери або колекції, його розмір відповідно збільшиться.

 - Щоб приховати або зменшити розмір `Future`, використовують heap-алокацію: `Pin<Box<dyn Future<Output = T> + Send>>` або розбивають логіку на менші `async fn` (щоб великий буфер не жив через `await`). Також можна використовувати `Arc`/`Box` для великих полів.

2) Що може статися, якщо `Future` буде занадто великою?

 - Великий `Future` означає більше пам'яті, яку потрібно копіювати/переміщати/зберігати при плануванні. Це може призвести до підвищеного використання пам'яті, збільшення розміру бінарника і повільнішої компіляції.
 - Якщо `Future` зберігається на стеку або у великих масивах, це може спричинити проблеми з використанням стеку або продуктивністю при переміщенні. Практично — зниження продуктивності, підвищений GC-подібний тиск (через часті алокації) або просто неочікуване зростання використання пам'яті.

 - Рішення: зменшити обсяг даних, що захоплюються через `await`, винести великі структури на heap (`Box`, `Arc`), або винести важку роботу в синхронні функції, викликані в `spawn_blocking`.

3) Чому `tokio` вимагає, щоб `Future` були `Send` у багатопотоковому рантаймі?

 - Multi-thread Tokio (новіший `Runtime` з `worker_threads`) може переміщувати завдання між потоками (work-stealing, балансування навантаження). Якщо `Future` не `Send`, його переміщення між потоками буде небезпечним.

 - Обмеження походить із системи гарантій Rust: `Send` гарантує, що значення можна безпечно переміщати між потоками. Щоб уникнути undefined behaviour, Tokio вимагає `Send` для `spawn`-лених задач у multi-thread рантаймі.

 - Якщо потрібно запускати `!Send` `Future`, варіанти: використовувати однопотоковий рантайм (`current_thread`), `LocalSet` + `spawn_local`, або реструктурувати код щоб прибрати непотокобезпечні захоплення.
