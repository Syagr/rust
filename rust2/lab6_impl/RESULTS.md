Benchmark results — lab6_impl

Дата: 2026-02-22

Команда запуску:

```bash
cargo run --release -- 8 50000
```

Результати (одноразовий запус):
- std `Arc+Mutex` time: 0.030527 s
- my `MyArc+MyMutex` time: 0.042562 s
- Percentage change (my vs std): +39.43% (my implementation slower на ~39%)

Короткий аналіз причин:
- `MyMutex` використовує простий spinlock (atomic compare_exchange + yield). Це створює більше витрат при високій конкуренції порівняно з оптимізованими ОС- або parking_lot-блокуваннями, які уникaють активного чекання.
- `std::sync::Mutex` надає більш оптимізовану реалізацію з врахуванням контекстних переключень та внутрішньої логіки для зниження contention (неактивне очікування / parking). Наш spinlock частіше викликає переходи між потоками і кеш-когерентні операції.
- Інші джерела накладних витрат: порядок пам'яті (`Acquire/Release`) та додаткові операції при створенні/знищенні `MyArc` (Box allocation/free). `std::Arc` і `std::Mutex` оптимізовані для мінімальної витрати в hot-path.

Рекомендації:
- Для реальних задач використовувати `std::sync` або `parking_lot` (краще масштабування).
- Якщо потрібно зменшити накладні витрати замість блокувань розглянути атомарні операції (`fetch_add`) або lock-free структури.
- Для порівняння запускати кілька повторів і брати медіану/середнє; тестувати на різних кількостях потоків.

Далі:
- Рекомендую запустити `cargo miri run -- <threads> <increments>` для невеликого набору (наприклад `4 1000`) щоб перевірити відсутність UB у debug/interpretive режимі.
- Можна замінити spinlock на більш просунутий механізм (parking) і повторити бенчмарк.
